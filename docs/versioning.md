# KeyPulse 版本与发布规范

适用对象：KeyPulse 全部发布版本。本文定义**版本号怎么升、什么时候绝不升主版本、一次发布要走哪些步骤**。与 `AGENTS.md` 的 Git 规范冲突时，以 `AGENTS.md` 为准；本文只补充版本与发布规则。

---

## 1. 基本原则

1. **遵循 [SemVer 2.0.0](https://semver.org/lang/zh-CN/)**：`MAJOR.MINOR.PATCH`，预发布加 `-rc.N` / `-beta.N`。
2. **版本号不是营销工具**。功能做得多不等于主版本要涨；`1.9.0` 完全可以是稳定成熟的 v1 版本。
3. **主版本克制**：`1.x` 长期演进。只有发生「用户无法平滑升级」的破坏性变更，且**没有可行的自动迁移方案**时，才允许 `2.0.0`。
4. **单一来源**：根目录 `VERSION` 文件是版本号的唯一来源。`build.sh` 用 `-ldflags -X` 注入 `internal/version`，`--version`、托盘提示、报告页脚、发布包目录名、tag、Release 标题全部由它派生，禁止在任何代码里另写一份版本号。
5. **已发布的版本永不覆盖**。发现问题就发新的 PATCH，不修改已上传的 tag / Release / 二进制。
6. **一次发布只做一件事**：一个版本号对应一组可描述的变更，不攒大包。

---

## 2. 升位决策

按顺序判定，命中即停：

```
① 是否命中 §3「主版本白名单」中的破坏性变更？
      └─ 是 → MAJOR（x+1.0.0），且必须附迁移方案与书面理由
② 是否新增了用户可感知、且向后兼容的能力？
      └─ 是 → MINOR（1.x.0），PATCH 归零
③ 其余一切变更
      └─ PATCH（1.1.x）
```

| 位 | 名称 | 何时 +1 | 合并变更后示例 |
|---|---|---|---|
| `MAJOR` | 主版本 | 破坏兼容且无法自动迁移 | `1.9.3 → 2.0.0` |
| `MINOR` | 次版本 | 新增向后兼容的能力 | `1.1.4 → 1.2.0` |
| `PATCH` | 修订版本 | 修复、性能、重构、文档、测试、构建 | `1.1.4 → 1.1.5` |

**PATCH 适用于**：修 bug、修统计口径偏差、性能优化、内部重构（行为不变）、补测试、改文案、改文档、改构建脚本、升级 Go 版本或依赖（只要产物行为不变）、修安全缺陷且不影响数据格式。

**MINOR 适用于**：新增报告视图、新增统计维度、新增带默认值的 CLI 参数、新增设置开关、接入 Wails 原生窗口、新增导出格式、新增组合键白名单计数、开机自启选项。前提是**老数据能读、老参数能用、老口径没变**。

## 3. 主版本克制清单（本项目的核心约束）

### 3.1 以下情况**绝不**升 `2.0.0`

| 情况 | 正确版本 |
|---|---|
| 新增视图、新增统计维度、新增报告页面 | MINOR |
| 换 UI 框架（例如从浏览器改为 Wails 原生窗口） | MINOR |
| 大规模重构、换内部数据结构、减少内存占用 | PATCH（若顺带新增能力则 MINOR） |
| 修复统计偏差、修复崩溃、修复钩子掉线 | PATCH |
| 升级 Go 版本、升级依赖、改构建脚本 | PATCH |
| 文档、测试、CI、代码风格调整 | PATCH |
| `.bin` 增加**可选**字段、旧版可忽略、新版能读旧文件 | MINOR |
| 报告内嵌 JSON 增加字段、页面新增渲染模块 | MINOR |
| 一次攒了很多功能 | 按实际影响定 MINOR，**不得**因此升 MAJOR |
| 觉得「1.x 听着不够正式」「想重新发个大的」 | 不升版本，直接发 PATCH/MINOR |

### 3.2 只有以下情况允许 `2.0.0`

1. **数据格式不可读回**：`.bin` 结构变更导致旧文件无法被新版读取，且无法提供自动迁移。
2. **统计口径根本改变**：历史数据与新数据不可比且无法并列呈现（例如把长按连发改为强制计入且不可配置）。
3. **已公开接口语义被删改**：删除或改变 CLI 参数且不提供兼容别名；CSV 列名/含义改变导致既有消费方失效。
4. **运行环境不再向后兼容**：最低 Windows 版本或 CPU 架构要求提升，导致已支持的环境无法运行。
5. **隐私模型改变**：开始记录原始按键序列、字符文本、窗口标题，或引入联网/遥测。**这类变更即使技术上兼容，也必须升 MAJOR 并单独公告**，因为它改变了用户对本工具的信任前提。

### 3.3 主版本的额外门槛

- 必须在 `CHANGELOG.md` 中以 `**破坏性**` 开头逐条写明，并说明**为什么无法保持兼容**。
- 必须提供迁移路径：旧数据转换脚本，或至少明确的「旧数据如何保留 / 导出」说明。
- 必须单独一次评审记录，不能夹带在功能发布里顺手升。
- 必须在 Release 说明里写明升级前备份 `%LOCALAPPDATA%\KeyPulse\`。

---

## 4. `1.x` 内的演进节奏

```
1.0.0        首个稳定基线
1.0.1        修一个统计/显示 bug
1.1.0        新增一个可感知能力（例如组合键白名单计数）
1.1.1        修这次新能力的 bug
1.2.0        下一个能力（例如 Wails 原生窗口）
...
1.9.x        功能累积很多，但仍是 v1 —— 这是正常且期望的状态
2.0.0        仅当 §3.2 命中
```

- **MINOR 一次一个主题**，不要把「Wails 窗口 + 开机自启 + 设置页」塞进同一个 `1.2.0`。
- **PATCH 可以随时发**，不受节奏限制；修好就发，不等攒够。
- v2 待办（见 `TODOS.md`）默认全部按 MINOR 规划，不预设任何主版本升级。

---

## 5. v1 兼容承诺

在 `1.x` 生命周期内，以下约定不得破坏：

| 项 | 承诺 |
|---|---|
| `.bin` 文件 | magic `KP01` + version 字段；新增字段只能追加且旧版可忽略，新版必须能读全部历史文件 |
| 数据目录 | `%LOCALAPPDATA%\KeyPulse\`，文件名 `YYYYMMDD.bin` |
| CLI 参数 | 只增不删；已有参数的含义不变，新增参数必须带默认值 |
| CSV 导出 | 表头只追加列，不改已有列名与含义 |
| 报告路由 | `#today` / `#day=YYYYMMDD` / `#week=YYYYMMDD` / `#all` 保持可解析 |
| 升级 | 覆盖 exe 即完成升级，历史数据不清零、不需要手动迁移 |

破坏以上任一条即命中 §3.2。

---

## 6. 预发布版本

- 格式：`1.2.0-rc.1`、`1.2.0-beta.2`，直接写入 `VERSION`。
- tag 为 `v1.2.0-rc.1`，GitHub Release 必须勾选 **pre-release**，不得设为 latest。
- 预发布不改 `CHANGELOG.md` 的正式版本条目，在 `Unreleased` 区记录。
- 正式发布时把 `VERSION` 改为 `1.2.0`，预发布资产保留不删，便于回溯。

---

## 7. 发版 SOP

每一步都不可跳过：

| # | 步骤 | 命令 / 产物 |
|---|---|---|
| 1 | 按 §2 判定升位，确定版本号 | 人工决策，MAJOR 需 §3.3 评审 |
| 2 | 更新根目录 `VERSION` | 单行、无换行外的空白 |
| 3 | 把 `CHANGELOG.md` 的 `Unreleased` 归入新版本，写日期与变更分类 | 见 §9 |
| 4 | 运行版本校验 | `bash scripts/check-version.sh` |
| 5 | 全量测试与页面回归 | `go test -buildvcs=false -count=1 ./...` / `node scripts/check-page.js <report.html>` |
| 6 | 生成发布包 | `bash scripts/package-release.sh` → `dist/KeyPulse-<版本>/` + zip + 直下 exe + `SHA256SUMS.txt` |
| 7 | 人工过一遍实机自测清单 | `docs/release.md` 第 4 节（10 条） |
| 8 | 同步文档 | README / metrics / release / TODOS 与新版本行为一致 |
| 9 | 提交并打 tag | 中文提交信息；`git tag -a v<版本> -m "release: 发布 v<版本>"` |
| 10 | 推送 | `git push && git push origin v<版本>` |
| 11 | 创建 GitHub Release | 标题 `v<版本>`，正文取自 CHANGELOG，见 §8 |
| 12 | 上传资产 | `KeyPulse-<版本>-win-x64.exe` + `KeyPulse-<版本>-win-x64.zip` + `SHA256SUMS.txt` |
| 13 | 回填台账 | `TODOS.md` 标记完成，未竟事项移入下个版本 |

**回滚**：tag / Release 一旦公开不删除。若构建包有问题，发布新的 PATCH 并在 Release 说明里注明「请勿使用 vX.Y.Z」，不要覆盖旧资产。

## 8. Tag、Release 与资产命名

| 对象 | 规范 | 示例 |
|---|---|---|
| Git tag | `v` + `VERSION`，annotated tag | `v1.1.0` |
| Release 标题 | `v<版本>`，可选加一句主题 | `v1.2.0 · 原生窗口` |
| Release 正文 | 直接取自 `CHANGELOG.md` 对应版本，附校验和、已知限制、Defender 提示 | — |
| 单文件 exe | `KeyPulse-<版本>-win-x64.exe` | `KeyPulse-1.1.0-win-x64.exe` |
| 压缩包 | `KeyPulse-<版本>-win-x64.zip`（完整发布包） | `KeyPulse-1.1.0-win-x64.zip` |
| 校验文件 | `SHA256SUMS.txt`（包内与上传资产各一份） | — |
| 示例报告 | 随包附带 `example-report.html`，不单独上传 | — |

- 单文件 exe 与包内 `keypulse.exe` 是同一份字节；`SHA256SUMS.txt` 已覆盖其哈希，Release 正文需写明资产名与校验行的对应关系。
- 只有稳定版可设为 latest；预发布一律勾 pre-release。
- 资产里**不放源码**、不放 `.tmp/`、不放 `.workbuddy/`、不放任何真实采集数据。
- Release 正文必须写明：适用系统、构建环境、`SHA256SUMS.txt` 校验方式、数据不会因升级清空。

## 9. CHANGELOG 规范

采用 Keep a Changelog 结构，中文书写，每条描述**用户可感知的效果**，不写 commit hash、不写内部函数名。

```markdown
## [1.1.0] - 2026-11-20
### 新增
- 设置页可开关「长按连发是否计入」，默认保持关闭。
### 变更
- 周报翻周时保留当前选中的日期筛选。
### 修复
- 修复跨零点后首个小时计数归错日期的问题。
### 安全
- 报告模板转义用户数据目录路径，避免本地文件注入。
```

分类固定为：`新增` / `变更` / `修复` / `移除` / `安全` / `文档`。破坏性变更用 `**破坏性**` 前缀，并在开头单列「升级须知」。

`Unreleased` 区常驻顶部；每次发版后清空该区、新建下一版本的空 `Unreleased`。

---

## 10. 提交规范（与 `AGENTS.md` 第 7 条对齐）

- 提交信息使用**中文**，格式 `<type>: <简述>`。
- `type`：`feat` / `fix` / `perf` / `refactor` / `docs` / `test` / `build` / `release`。
- 单次提交对应一个独立功能点；发版提交单独一次：`release: 发布 v1.1.0`。
- 提交前按 `AGENTS.md` 第 9 条检查暂存区：不得包含 Token、密码、本机绝对路径、真实 `.bin` 数据、`.env.local`。

---

## 11. 自动校验

`bash scripts/check-version.sh` 覆盖：

1. `VERSION` 格式合法（`X.Y.Z` 或 `X.Y.Z-<pre>`）。
2. `CHANGELOG.md` 中存在该版本的正式条目（预发行版查 `Unreleased`）。
3. 该版本的 tag 尚未存在（防止重复发布）。
4. README / 文档中没有写死的旧版本号（版本号只应出现在 `VERSION` 与 `CHANGELOG`）。
5. 输出本次应使用的 tag 名、Release 标题、资产文件名，供后续步骤复制。

`scripts/package-release.sh` 在打包前调用本校验，校验不通过直接中止。
